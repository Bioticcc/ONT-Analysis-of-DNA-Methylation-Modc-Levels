## Script corrections

The revised stage 01:

- uses a Minimap2 index explicitly built with the `lr:hq` preset;
- aligns one of the 74 source BAMs at a time with Dorado `--no-sort`;
- writes to a partial filename, fully decompresses it, validates its tags, then
  renames it atomically;
- skips an unchanged chunk after an interruption only when a versioned marker
  matches its byte size and modification time;
- records the validation method, alignment-record count, byte size,
  modification time, and validation timestamp in each completion marker;
- recoverably quarantines and regenerates any completed chunk that fails a
  full-stream check;
- uses 20 alignment threads and a lower process priority;
- writes timestamped logs and five-minute resource heartbeats.

The revised stage 02:

- refuses to run unless the exact 74 expected aligned chunks are present;
- fully decompresses every BAM, records per-chunk byte and alignment-record
  counts in a validation manifest, and verifies MM, ML, and MN tags;
- performs a single controlled Samtools coordinate sort using 12 threads and
  2 GiB per sort thread;
- fully decompresses the sorted partial BAM and requires its alignment-record
  count to equal the summed input count before promotion;
- writes the final BAM and index through partial files and atomic renames;
- writes timestamped logs and five-minute resource heartbeats.

A 1,000-read integration test confirmed that Dorado accepts an `lr:hq` index,
produces a valid BAM, and preserves separate 5mC/5hmC MM/ML/MN tags.

## Stage 02 CRC incident and Stage 01 repair

The 2026-08-28 Stage 02 attempt failed during the concatenation/sort pipeline
with a BGZF CRC32 mismatch and `samtools sort: truncated file`. Mapping the
reported concatenated block offset to the inputs and then fully streaming the
individual BAMs identified exactly one damaged aligned output:

```text
PBO06467_pass_969d9163_b9126d6d_5.aligned.unsorted.bam
```

The corresponding unaligned source BAM passed a complete stream check and
contained 352,666 records. The former scripts had accepted the aligned BAM with
`samtools quickcheck`, which verifies the header and terminal block but does not
decompress every intermediate BGZF block. No kernel disk-I/O error was retained
around the incident, so the evidence establishes corrupted file content but not
the underlying hardware or interruption that produced it.

The strengthened Stage 01 detected the same CRC failure, moved the damaged
3,865,771,858-byte BAM and its legacy empty marker to the run-stamped
`tmp/stale_alignment_partials/.../invalid_completed_chunks/` quarantine, and
realigned only that intact source. Dorado consumed all 352,666 reads; the new
BAM contains 816,211 alignment records because mapped reads can contribute
primary, secondary, and supplementary records. The replacement passed an
independent full decompression scan.

Stage 01 then completely streamed all other aligned chunks and upgraded their
legacy empty markers. Final inventory: 74 aligned BAMs, 74 versioned markers,
zero empty markers, and no second corrupt chunk. The quarantined original is
retained for recovery/audit and must not be removed without explicit approval.

## Stage 03 replacement and audit

The Qwen-written Stage 03 script was discarded rather than patched. The
replacement uses Samtools for alignment statistics and a single Mosdepth pass
for run-length depth, chromosome summaries, fixed windows, and breadth counts.
A standard-library Python helper validates that Mosdepth covers every FAI base,
that threshold counts are monotonic and bounded by interval length, and that
per-base, chromosome, window, and total counts agree before outputs are
promoted.

The end-to-end integration test used a coordinate-sorted and indexed chrM BAM
containing one mapped read plus modified-base tags. Mosdepth and the Stage 03
helper reported:

- 16,299 reference bases;
- 426 bases at >=1x;
- mean depth 0.026137x;
- no bases at >=5x, >=10x, or >=20x.

An independent `samtools depth -aa -Q 0 -G 1796` calculation reproduced every
one of those counts and the mean exactly at six decimal places. The test also
validated all BGZF indexes, immediate restart/skip behavior, `--check-only`,
and recoverable `--force` archiving. During restart testing, a shared heartbeat
file-descriptor inheritance issue was found and corrected in
`scripts/lib/pipeline_common.sh`; consecutive invocations now acquire and
release the lock successfully.

## Stage 04 implementation and audit

Stage 04 was implemented as one Modkit analysis stage with a standard-library
Python validation and aggregation helper. The script runs the full Modkit tag
check, a matched all-context summary, a strand-combined CpG pileup retaining
separate `m` and `h` rows, and a chromosome-level `modkit stats` summary.

The audit found that Modkit 0.6.4 `summary --cpg` may include modification-tag
counts from unmapped records in its totals. The pipeline therefore does not use
that command as a CpG denominator. Final CpG quantities come directly from the
indexed pileup, and `modkit_cpg_summary.txt` is produced by `modkit stats` over
that pileup. The all-context summary uses `--matched-only` and remains clearly
labelled informational.

The end-to-end chrM integration test confirmed:

- full MM/ML/MN validation and discovery of exactly `C:m` and `C:h`;
- paired 5mC/5hmC bedMethyl rows and valid BGZF/Tabix indexes;
- 287 reference CpG dyads, 8 dyads with valid calls, and 8 valid cytosine calls
  in the tiny one-mapped-read fixture;
- exact equality of `valid = 5mC + 5hmC + canonical` at every emitted site;
- complete global, chromosome, 1 kb test-window, call-coverage, report, and
  manifest outputs;
- immediate restart/skip, check-only, and recoverable force-rebuild behavior.

A separate nonzero-count fixture reproduced 60% 5mC, 20% 5hmC, 80% total
modified, 20% canonical, and a 75%/25% split of modified calls exactly from the
provided numerators and denominators.
